MCPサーバーを一つ足しただけで、作業を始める前にトークンがごっそり消える。長いセッションが途中から急に遅く・高くなる。こうした現象の裏側には、プロンプトの「並び方」とキャッシュの関係がある。本記事では、プロンプトがどう組み立てられ、キャッシュが何をどこに保存し、なぜ順番が効くのかを、順を追って分かりやすく説明する。

## プロンプトはどう組み立てられるか

APIリクエストは tools → system → messages の順に一列に並ぶ。ツール定義が先頭、次にシステムプロンプト、最後に会話メッセージだ。

設計上の要点は「プロンプト組み立てをセッション状態の純粋関数にする」こと。同じ状態からは常にバイト単位で同一のプロンプトが出るようにし、タイムスタンプ・ランダムID・シリアライズ順序の揺れといった非決定的な要素を安定した先頭部分に混ぜない。これがキャッシュを安定して効かせる前提になる。

もう一つ興味深いのは、マルチエージェントの協調がコードではなくシステムプロンプトの指示として書かれていること。サブエージェントは特別なプロセスではなく、異なるシステムプロンプトを与えられたClaudeのインスタンスにすぎない。「プロンプト＝アーキテクチャ」という考え方だ。

## プレフィックスとは

キャッシュの話に入る前に、鍵となる「プレフィックス（prefix）」を押さえる。prefixは接頭辞、つまり**先頭から始まる連続した一部分**のこと。`ABCDEFG` なら `A`, `AB`, `ABC` … はすべてprefixだが、途中の `BCD` や末尾の `EFG` はprefixではない。「先頭から切れ目なく続いていること」が条件だ。

リクエストにおけるプレフィックスは、先ほどの並び（tools → system → messages）の先頭からの連続部分を指す。キャッシュはこの「先頭からどこまでが前回と一致するか」だけを見る。

![リクエストの並びとキャッシュ命中範囲](/blog/assets/img/prompt-order-cache-hit.svg)

先頭の安定した部分（ツール・システム・直近以外の履歴）が前回と同じなら、その範囲をまるごと再利用できる。逆に、途中の1か所が変わると、そこから後ろは変わっていなくても全部作り直しになる。

なぜ「途中が変わると後ろが全滅」なのか。モデルは文章を前から順に読み、各トークンの意味を「それまで読んだ全部」を踏まえて計算するからだ。3番目のトークンの状態は1・2番目に依存して決まる。だから途中の1文字が変われば、そこから先の計算結果は前回と別物になる。キャッシュが「先頭から連続で一致した範囲だけ」しか再利用できないのは、このためだ。

## キャッシュは何を・どこに保存するか

保存されるのはプロンプトの生テキストや応答ではない。プレフィックスを処理したときにattention層が計算した **KVキャッシュ（Key/Valueテンソル）** だ。

置き場所はAnthropicのサーバー側、具体的にはリクエストを処理したGPUのメモリ（VRAM）上。モデルごとに分離され、TTL（5分、または1時間）だけ生存する一時的なものだ。公式ドキュメントでも、KVキャッシュ表現とキャッシュ内容のハッシュはメモリ上にのみ保持され、ディスクに永続化されないと明記されている。つまり「会話を保存して使い回している」のではなく、「計算済みの中間状態を数分だけメモリに置いている」だけだ。

## なぜ読み込みが安いのか

推論で最も重いのは **Prefill** ——入力トークン全体にわたってattentionを計算する工程で、コストは文脈長にほぼ二次で増える。キャッシュが命中すると、このPrefillをまるごとスキップし、VRAMにある計算済みK/Vテンソルをそのままattention層へ流し込む。GPUの計算をやり直さずに済むので、読み込みは通常入力の10%（0.1×）で課金される。90%引きの正体は「再計算をしないこと」だ。

![キャッシュの中身と、読み込みが安い理由](/blog/assets/img/kv-cache-mechanism.svg)

ただし厳密には無料ではない。内訳は、書き込み（初回）が1.25×（5分TTL）または2×（1時間TTL）、読み込みが0.1×。5分TTLなら1回命中すれば書き込みの割増を取り戻し、以降は純粋な節約になる。

唯一「無料」なのはTTLのリフレッシュだ。ヒットするたびに5分の生存期間が追加料金なしで延長される。すでにVRAMに載っているテンソルの生存を少し延ばすだけで、Anthropic側の追加計算がゼロだからだ。

## 「静的を先、動的を後」の実践

原則を実装に落とすと、次の4点になる。

- **並び順を守る。** 変わらないもの（ツール定義、システム指示、静的な文脈）を先頭に、変わるもの（ユーザー入力）を末尾に置く。ブレークポイントは最後のsystemブロックに1つ置けば、toolsとsystemがまとめてキャッシュされる。
- **安定プレフィックスに変動要素を混ぜない。** よくある事故が、システムプロンプトに現在時刻を差し込むこと。タイムスタンプが1か所入るだけで、それ以降が全部キャッシュ対象外になる。日付が変わった等の理由でシステムプロンプトを書き換えず、更新情報は後ろのメッセージ側に足す。
- **決定性を守る。** JSONのキー順やツールスキーマの並びが毎回揺れるとバイト不一致を生む。ツールは名前でソートして常に同じ順に並べ、「同じ状態→同じバイト列」を徹底する。
- **動的に増えるツールはメッセージ側へ。** 検索で発見したツールはsystemプレフィックスに差し込まず、会話履歴側に追加する。プレフィックスが無傷のまま保たれ、ツールを増やしてもキャッシュ命中を維持できる。

## つまづきやすい点

キャッシュはモデルごとに分離されている。セッション途中でモデルを切り替えると、内容が同一でも全体が再計算される。同じ理由で、CLAUDE.mdやルール、MCP構成をセッション途中で変更するとキャッシュが壊れる。設定はセッション開始前に固めておくのが安全だ。「速く始まったセッションが途中から遅くなる」現象の多くは、こうした変更でプレフィックスが変わり、キャッシュ命中を失っていることが原因になる。

なお仕様上の制約として、ブレークポイントは1リクエストにつき最大4個、各ブレークポイントは最大20コンテンツブロックまで遡って過去のキャッシュを探す。最小キャッシュ長は1,024トークン。長い会話ではブレークポイントの位置に注意がいる。

## まとめ

プロンプトは tools → system → messages の順に並び、キャッシュは先頭からの連続一致（プレフィックス）だけを再利用する。保存されるのは計算済みのK/VテンソルでVRAM上に一時的に置かれ、命中時はPrefillを飛ばせるから読み込みが10%で済む。だから設計の勘所はただ一つ、「変わらないものを先、変わるものを後」に並べ、その先頭部分を毎回バイト単位で同一に保つことに尽きる。
