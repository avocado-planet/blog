特定のサイトにアクセスすると、ブラウザが「クライアント証明書を選択してください」と求めてくることがあります。これは **mTLS(相互TLS認証 / クライアント証明書認証)** という仕組みです。この記事では、その仕組みを順番に整理します。

## 1. mTLSとは

通常のHTTPSでは、**サーバーだけ**が証明書を提示し、クライアントがそれを検証します。mTLSでは、**サーバーもクライアントを証明書で検証します**。

| | 通常のHTTPS | mTLS |
|---|---|---|
| サーバー証明書 | 必要 | 必要 |
| クライアント証明書 | 不要 | **必要** |
| 本人確認 | ID・パスワードなどで別途 | 証明書で通信の時点で確認 |

よくある用途は次のとおりです。

- 社内システム、VPN、ゼロトラスト型のプロキシ
- 金融・官公庁系のAPI
- AWS API Gateway / ALB、OCI API Gateway のmTLS
- サービス間通信(Istio などのサービスメッシュ)

### 「秘密鍵を求められる」の正体

秘密鍵そのものがサーバーに送られることはありません。**秘密鍵は署名を作るために、クライアント側で使われるだけ**です。ブラウザやOSで、鍵ストアの選択やパスワード入力のダイアログとして表示されるのは、このためです。

## 2. 通信の流れ

![mTLSハンドシェイクの流れ](/blog/assets/img/mtls-client-certificate-guide-handshake.svg)

1. クライアントが `ClientHello` を送る。
2. サーバーが `ServerHello` と**サーバー証明書**を返す。クライアントは、これを自分のCAストアで検証する。
3. サーバーが `CertificateRequest` で、**クライアント証明書の提示を要求**する。
4. クライアントが**クライアント証明書**と、**秘密鍵で作った署名**(`CertificateVerify`)を送る。
5. サーバーが、CA検証と署名検証を行う。
6. 双方が `Finished` を送り、鍵交換が完了する。
7. 暗号化された通信が始まる。

図の橙色が、通常のHTTPSにはないmTLS特有の手順です。

## 3. CAによる検証の詳細

サーバーは、クライアント証明書を次の観点で確認します。

![信頼の鎖とサーバーが行う確認](/blog/assets/img/mtls-client-certificate-guide-chain.svg)

サーバーは事前に、**信頼するCAの証明書(信頼アンカー)**を持っています。クライアントが提示した証明書から、そこまで鎖をたどれれば信頼します。

| 確認項目 | 内容 |
|---|---|
| 署名の検証 | 上位CAの公開鍵で署名を検証し、改ざんがないか確認 |
| 信頼の鎖 | クライアント証明書、中間CA、ルートCAとたどれるか |
| 有効期限 | `Not Before` と `Not After` の範囲内か(時刻ずれにも注意) |
| 失効確認 | CRL(失効リスト)またはOCSP(オンライン照会)で、無効化されていないか |
| 用途 | EKU(拡張鍵用途)に `clientAuth` が含まれるか |
| 秘密鍵の所有 | `CertificateVerify` の署名を、証明書内の公開鍵で検証 |

証明書は公開情報なので、盗み見て提示するだけではなりすませません。**秘密鍵の所有確認**があるから、本人確認として成立します。

### CA検証と、アクセス許可は別

CA検証は「本人確認」です。サーバー側では、さらに次のような絞り込み(認可)もできます。

- Subject(CN など)や SAN が許可リストに含まれるか
- 特定の発行CA(中間CA)のみ許可する
- 証明書のフィンガープリントで個別に許可する

### よくあるエラー

| エラー | 主な原因 |
|---|---|
| `400 No required SSL certificate was sent` | クライアント証明書を提示していない |
| `unknown ca` | 発行CAがサーバーの信頼ストアにない |
| `unable to get local issuer certificate` | 中間CA証明書が欠けている |
| `certificate has expired` | 有効期限切れ、または時刻ずれ |
| `certificate revoked` | 失効済み |
| `unsupported certificate purpose` / `bad certificate` | EKU に `clientAuth` がない |

手元で検証するコマンドです。

```bash
# CAチェーンで検証
openssl verify -CAfile ca.crt -untrusted intermediate.crt client.crt

# 有効期限・EKU・発行者の確認
openssl x509 -in client.crt -noout -dates -issuer -subject -ext extendedKeyUsage
```

## 4. サーバー証明書とクライアント証明書のCAは同じ?

**同じでも別でもよく、CAは特定のサーバーに属するものではありません。** 検証する側が、それぞれ「どのCAを信頼するか」を決めます。

| 検証する側 | 検証する証明書 | 使う信頼ストア |
|---|---|---|
| クライアント | サーバー証明書 | クライアント(ブラウザ・OS)が持つCA |
| サーバー | クライアント証明書 | サーバーに登録したCA |

信頼ストアが別々なので、2つの証明書のCAが異なっていても問題ありません。

| パターン | サーバー証明書 | クライアント証明書 | 主な用途 |
|---|---|---|---|
| A. 別CA(最も一般的) | 公的CA | 自社の**プライベートCA** | 社内システム、API、ゼロトラスト |
| B. 同じプライベートCA | 自社CA | 同じ自社CA | 閉じた環境、サービス間通信 |
| C. 公的CA | 公的CA | 業務用の公的CA | 電子申請など、官公庁・金融系 |

パターンAが多いのは、クライアント証明書は**自社で発行・失効・期限を管理できる方が運用しやすい**ためです。

### CAの秘密鍵はどこに置く?

- 通常のWebサーバーには**置きません**。侵害されると、証明書を無制限に発行されてしまうためです。専用のCAサーバー、HSM、クラウドの管理サービスなどで厳重に保管します。
- サーバーに登録するのは、**CAの証明書(公開情報)だけ**です。
- クラウドの例: AWS の ACM Private CA、OCI の Certificates サービス。API Gateway / ALB のmTLS設定では、信頼するCA証明書(トラストストア)をアップロードします。

## 5. CSRとは

**CSR(Certificate Signing Request:証明書署名要求)**は、CAに「この公開鍵に対して証明書を発行してください」と依頼するためのファイルです。

含まれるもの:

- 公開鍵
- 申請者の情報(Subject): CN、O、C など
- 申請者の秘密鍵による署名(鍵を持っていることの証明)

**秘密鍵は含まれません。** 秘密鍵は作成者の手元に残り、CAには渡りません。

```bash
# 秘密鍵を作成
openssl genrsa -out client.key 2048

# CSRを作成
openssl req -new -key client.key -out client.csr \
  -subj "/C=JP/O=Example/CN=taro-client"

# CSRの中身を確認
openssl req -in client.csr -noout -text
```

## 6. .p12ファイルとは

`.p12` は **PKCS#12** 形式のファイルです(`.pfx` も同じ形式)。**証明書と秘密鍵を1つにまとめ、パスワードで暗号化したコンテナ**で、配布やインポートに便利なため使われます。

含まれるもの:

- クライアント証明書
- 秘密鍵
- 中間CA、ルートCA証明書(含まれる場合があります)

注意点:

- 秘密鍵が入っているため、**パスワードと同じ経路(同じメールなど)で送らない**でください。流出すると、なりすましが可能になります。
- 日常的には、ブラウザやOSの鍵ストアにインポートして使います。

```bash
# 中身の確認
openssl pkcs12 -info -in client.p12

# PEM形式に分離
openssl pkcs12 -in client.p12 -clcerts -nokeys -out client.crt
openssl pkcs12 -in client.p12 -nocerts -nodes -out client.key

# PEMから .p12 を作成
openssl pkcs12 -export -inkey client.key -in client.crt -certfile ca.crt -out client.p12
```

OpenSSL 3.x で古い `.p12` を開くと `unsupported` エラーが出ることがあります。その場合は `-legacy` オプションを付けてください。

curl で接続する例です。

```bash
curl --cert client.crt --key client.key --cacert ca.crt https://example.com/

# .p12 を使う場合
curl --cert-type P12 --cert client.p12:パスワード https://example.com/
```

## 7. 一般的な運用の流れ

![クライアント証明書の運用フロー](/blog/assets/img/mtls-client-certificate-guide-flow.svg)

1. **CAを用意する**(社内CAまたは商用CA)。
2. **サーバーにクライアント認証を設定する**(信頼するCA証明書を登録)。
3. **利用者が秘密鍵とCSRを作成する**。秘密鍵は端末内に保管します。
4. **CAがCSRに署名して発行する**(用途は `clientAuth`)。
5. **利用者が証明書を受け取り、導入する**(`.p12` をインポート)。
6. **接続テストと運用**(更新、失効の管理)。

クライアント証明書の受け取り方には、二通りあります。

- **A. 利用者がCSRを作る方式**: 発行された `.crt` だけを受け取ります。鍵が外に出ないため、より安全です。
- **B. 管理者が鍵ごと発行する方式**: ポータルで `.p12` をダウンロードし、パスワードを別経路で通知します。社内システムで多い方式です。

運用で決めておくこと:

- 有効期限(1〜2年が多い)と更新の手順
- 退職・紛失時の失効手続き
- 失効の確認方法(CRL / OCSP)

## 8. 証明書は全員で共有してよい?

**共有は避けてください。** 人(または端末)ごとに、別々のクライアント証明書を発行するのが一般的です。

共有が好ましくない理由:

- **誰がアクセスしたか分からない**: ログのSubjectが全員同じになり、監査・追跡ができません。
- **個別に失効できない**: 1人が退職・紛失・流出すると、失効により全員が使えなくなります。
- **秘密鍵の流出リスクが大きい**: 配布経路が増え、漏れる可能性が高まります。
- **証明書認証の利点が失われる**: 本人確認としての意味がなくなります。

| 単位 | 例 | 発行の方法 |
|---|---|---|
| 利用者ごと | 社員ごとの証明書 | 入社時に発行、退職時に失効 |
| 端末ごと | PC・スマホごとの証明書 | MDM(Intune、Jamf など)で自動配布 |
| システムごと | バッチ、アプリ、マイクロサービス | システム単位で発行(人とは別) |

端末ごとの発行では、MDMによる自動配布が増えています。利用者が手動で `.p12` を扱わずに済み、鍵の管理も安全になります。

## まとめ

- mTLSは、**サーバーとクライアントが、互いに証明書で相手を確認する**仕組みです。
- 秘密鍵は送られず、**署名を作るために手元で使われる**だけです。
- サーバーは、**信頼するCAの証明書**を持ち、署名・鎖・期限・失効・用途・鍵の所有を確認します。
- サーバー証明書とクライアント証明書のCAは、**別でも同じでもよく**、クライアント側は自社のプライベートCAで発行するのが一般的です。
- **CSR** は発行依頼書、**.p12** は証明書と秘密鍵をまとめたファイルです。
- 証明書は、**人または端末ごとに発行する**のが基本です。
