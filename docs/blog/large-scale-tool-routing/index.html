Agent AI CLIで数百のツール/スキルを効率よくルーティングする — retrieve-then-load 実践ガイド

July 04, 2026 | 1 Minute Read

AIエージェントにツールを追加していくと、いつか必ず「全部をコンテキストに載せきれない」壁にぶつかる。MCPサーバーを数個つないだだけでも、作業を始める前に数万トークンがツール定義で消える。本記事では、ツール/スキルが数百規模になったときに効率よくルーティングするための設計と、LangGraph ReActベースの自作CLIへの落とし込みを整理する。

核心は「検索してから読み込む」

答えは一つに集約される。全ツール定義を事前にコンテキストへ載せない。代わりに、クエリに応じて関連ツールを検索し、上位数個だけを読み込む「retrieve-then-load」の2段構えにする。

Anthropicもこれを Tool Search Tool として製品化しており、defer_loading: true でマークしたツールは事前ロードせず、必要時に動的ディスカバリする仕組みになっている。2026年1月14日からは Claude Code の MCP にもデフォルト適用されている。

図の色分けは、灰=データ源、青=検索パイプライン、橙=コンテキスト/実行、紫=バイパス（常時ロード）を表す。数百のツール定義をインデックス化しておき、クエリが来たら Retriever が上位3〜5個を取得、それだけを LLM のコンテキストに注入して ReAct ループを回す。頻出ツールは検索を経由せず常時ロードしておく。

規模別の戦略

ツール数によって取るべき手は変わる。

〜50個 — 全ロードでよい。検索層は不要で、起動時に bind_tools で全部渡すだけ。

50〜数百 — retrieve-then-load が最も効くレンジ。従来は50以上のMCPツールで作業前に約77Kトークンを消費するところ、Tool Search で約8.7Kに削減され、コンテキストの95%を温存できる（85%削減）。Anthropicの内部評価では、大規模ツールライブラリで Opus 4 が49%→74%、Opus 4.5 が79.5%→88.1%に精度改善したと報告されている。

数百〜数千 — 単一の検索だけでは精度が落ちるので、以下を重ねる。

  • 階層化（カテゴリ / namespace）: まずカテゴリ（ドメインやMCPサーバー単位）に絞り、その中でツールを検索する。検索空間を段階的に縮小できる。
  • マルチエージェント（Supervisor）: サブエージェントごとに専門ツールセット（各20〜30個）を持たせ、Supervisor がルーティングする。ただし各サブエージェント自体は128ツール上限に縛られるため、検索層との併用が前提になる。
  • Code Execution（コードモード）: ツールをファイルシステム上のコードモジュールとして提示し、モデルが必要なものだけ import して呼ぶ。定義をオンデマンドで読み、中間結果をコード側でフィルタしてからモデルに渡せる。ツール連鎖が多い場合に、中間結果のトークン往復を消せるのが強み。

検索エンジンの選択

Retriever の中身は、要件に応じて選ぶ。

方式 特徴 向く場面
BM25 / regex インデックス不要・軽量。説明文の質に依存 自作の最初の一手。Anthropicも tool_search_tool_bm25 / _regex を提供
Dense（embedding） 言い換え・意図に強い クエリ表現がツール名と乖離するケース
Hybrid（BM25 + dense, RRF） 最も堅い 本番運用
Graph RAG-Tool Fusion ツール間の依存（あるツールの出力が別ツールの引数）を扱う 連鎖前提のワークフロー

まず BM25 で計測し、不足分だけ Dense / Hybrid に上げる、という段階的な進め方が現実的だ。

LangGraph ReAct への実装

自作CLIに組み込むなら、手順はこうなる。

  1. ツールレジストリとインデックスを分離管理する。 起動時にツール説明文を BM25 かベクトルでインデックス化しておく。
  2. search_tools メタツールをループに追加する。 エージェントがこれを呼ぶと、ヒットしたツール定義だけを次ターンの bind_tools に動的注入する。つまりモデルノードに渡すツールリストをターンごとに差し替える。
  3. langgraph-bigtool を先に試す。 ツールレジストリへのセマンティック検索から動的バインドまで、まさにこのパターンを提供しているので、自作する前に挙動を確認する価値がある。
  4. Anthropic純正で済ませる場合は defer_loading: true と tool_search_tool_bm25_20251119（betaヘッダ advanced-tool-use-2025-11-20）を使う。最大10,000ツールまで対応し、1検索につき3〜5個の関連ツールを返す。Sonnet 4.5/4.6・Opus 4.5/4.6対応で、Haikuは非対応。
# イメージ: search_tools がヒットしたツールだけを次ターンにバインドする
def agent_node(state):
    query = state["messages"][-1].content
    hits = registry.search(query, k=5)          # BM25 / vector
    tools = [registry.get(name) for name in hits]
    model = llm.bind_tools(always_loaded + tools)  # 頻出ツール + 検索結果
    return {"messages": [model.invoke(state["messages"])]}

Skills も同じ問題

Skill はツールと別物に見えて、ルーティング問題としては同じだ。SKILL.md の description フィールドがクエリにマッチング判定される。つまり実質的に説明文検索である。数百のSkillでも、説明文をインデックス化して top-k を取得する同じ手法が効く。

落とし穴

検索精度がボトルネックになる。 Arcade.dev が4,027ツールで25の素直なワークフローを試したところ、regexで56%（25中14）、BM25でも64%（25中16）にとどまり、「send email」が Gmail_SendEmail を引けないといった、ありふれたツールの取りこぼしも起きている。対策は次の3点。

  • 説明文をキーワード豊富に、自然言語で書く。 Tool Search はツール名・説明・パラメータ名にマッチするため、具体的でキーワードの多い説明ほど発見されやすい。技術ジャーゴンより、利用者の言い回し（「会話レポートを送る」など）を入れる。
  • 頻出ツールは常時ロードする（defer_loading: false）。 毎セッションで使うツールは事前ロードが推奨されている。
  • BM25で計測してから段階的に上げる。 いきなりHybridを組むより、まず素朴なBM25でどこまで引けるかを測り、失敗パターンを見てからDense/Hybrid化する。

まとめ

数百ツール規模のルーティングは、「全部載せない → 検索して上位数個だけ載せる」という一点に尽きる。50〜数百なら retrieve-then-load 単体で十分効き、数千規模では階層化・マルチエージェント・コードモードを重ねる。そして最終的な性能を決めるのは検索精度、すなわちツール説明文の品質だ。まず langgraph-bigtool を1本動かして BM25 で精度を測り、足りなければ Hybrid 化する——この順序で進めるのが堅実だと考えている。
